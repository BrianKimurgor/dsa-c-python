How this book works

A course in data structures and algorithms that starts in C, where nothing is hidden, and finishes in Python, where everything you learned becomes a one-liner you actually understand.

Why C first, then Python

Every data structure is, underneath, a pattern of boxes in memory and rules for moving between them. Python hides the boxes. C makes you build them with your own hands. If you learn the structures in C, you will never again wonder what a Python list "really is" or why a dictionary lookup is fast. You will have built both.

That is also the entire reason systems engineering starts with C: operating systems, databases, network stacks, and the runtimes that run Python and PyTorch are written in C and C++. Learning C is learning to read the floor the rest of the building stands on.

How to read code

Reading code is a skill separate from writing it, and nobody teaches it. Here is a method that works for any language.

Beginners read code the way they read a novel: top to bottom, hoping meaning arrives. Experienced engineers read code the way a detective reads a room. They look for the entry point, follow the flow, keep a list of what changes, and test their theory against the evidence. Here is that method in seven steps.

  1. Find the entry point and follow the calls. In C, start at main. When it calls a function, jump to that function, read it, and jump back. The file order is not the reading order.
  2. Read the signature as a contract. int count_above(int a[], int n) says: give me an array and its length, I give you back a whole number. Guess what it does from the name before reading the body. Then check your guess.
  3. List the state. Which variables change during the function? Those are the moving parts. Everything else is scenery.
  4. Find the loop and ask two questions. What is true every single time we come back to the top? (That is the invariant.) What makes it stop?
  5. Trace it with a table. One column per changing variable, one row per step. Do it on paper for small inputs. The steppers in this book do exactly this.
  6. Predict the output, then run. If you were wrong, the code is not the problem; your model of the code is. Fix the model and trace again.
  7. Rename things in your head. i is "the position I'm looking at". tmp is "the value I'm holding while I swap". Short names in code are fine once you have a long name in your mind.

Take the smallest loop that does something. Press Step and watch the table grow one row each time the loop body runs. This is what you should be doing on paper for any loop you do not understand.

Variables, types, and bytes

A variable in C is a named box of a fixed size. The type says how big the box is and how to read the bits inside it.

In Python you write x = 5 and move on. In C you write int x = 5;, and that word int is a promise: this box is (almost always) 4 bytes, it holds a whole number, and it can go from about minus two billion to plus two billion. Step outside that and the number silently wraps around. C does not warn you; it assumes you knew.

Functions and pass-by-value

A function is a named piece of work with inputs and one output. C hands it copies of your variables, which is the key to understanding why pointers exist.

36 9 Hello, Brian 6

Pass-by-value, said plainly

When you call try_to_change(n), C does not send n. It sends the number 6, and the function stores that 6 in its own fresh box called v. Changing v changes that box, nothing else. When the function ends, its boxes are thrown away.

This is a feature. It means a function cannot accidentally wreck your variables. But it raises a question: what if you want a function to change something in the caller, like swapping two numbers? You have to hand it the address of the box instead of the contents. That is the entire reason pointers exist, and it is two chapters away.

Declaration before use

C reads your file top to bottom and must know a function's signature before it sees a call to it. Either define functions above main, as above, or put a prototype near the top: int square(int x); (note the semicolon, no body). Header files like stdio.h are just collections of prototypes.

Scope: where a name is visible

A variable declared inside { } exists only until the matching }. A variable declared inside a for header exists only in that loop. A variable declared outside every function is global: visible everywhere, alive for the whole program, and the source of many hard-to-find bugs. Keep variables as local as possible; it makes code easier to read because you know exactly where a value can change.

Arrays and strings

An array is a row of boxes of the same type, side by side in memory. A string is just an array of chars with a zero at the end. This is your first real data structure.

What an array looks like in memory

If scores begins at address 1000, then scores[0] is at 1000, scores[1] at 1004, scores[2] at 1008, and so on. The computer finds scores[i] by computing 1000 + i × 4. That multiplication is why array access is instant no matter how big the array is, and why index 5 is simply "address 1020", which belongs to someone else.

Arrays and functions

When you pass an array to a function, C does not copy the boxes. It passes the address of the first box. That has two consequences: the function can modify the caller's array (unlike plain ints), and the function has no idea how long the array is. That is why every array-taking function in C also takes a length: int sum(int a[], int n).

Pointers

A pointer is a variable whose value is an address. That is the whole definition. Everything confusing about pointers is syntax, not concept.

Every box in memory has a number: its address. A pointer is a box that stores one of those numbers. With a pointer you can say "go to that address and read what is there" or "go to that address and write this". Two symbols do all the work:

  • &x means the address of x. "Where does x live?"
  • *p means the thing at the address stored in p. "Go where p points."

Step through this. Watch the memory table, not just the message.

The swap that finally works

Remember try_to_change from the functions chapter? It received a copy and could not reach the original. Pass the address instead and the function can reach straight into the caller's box.

This pattern, "pass the address so the function can modify it", is how every C function returns more than one thing, how scanf fills your variables, and how linked lists, trees, and every other structure in Part 2 are stitched together.

Pointers and arrays are cousins

This is why a function that receives an array can be written as int sum(int *a, int n) or int sum(int a[], int n). They are the same declaration. The array decays to a pointer to its first element, and the length is lost, which is why you pass n.

NULL and the crash you will meet

NULL is the address zero, which means "points to nothing". Reading or writing through a NULL pointer crashes the program with a segmentation fault. You will see this message many times. It means: somewhere, you followed a pointer that did not point anywhere valid. Every pointer should either point at something real or be NULL, and you check for NULL before following it.

The four bugs you will write

  1. Leak. You malloc and never free. The program slowly eats memory. Harmless in a 2-second program, fatal in a server that runs for weeks.
  2. Use after free. You free, then read or write through the old pointer. Sometimes it works, sometimes it corrupts something unrelated.
  3. Double free. You free the same pointer twice. The allocator's bookkeeping breaks; expect a crash.
  4. Returning a stack address. int a[10]; return a; hands back memory that no longer exists.

On WSL, compile with -fsanitize=address and all four are reported with the exact line. Or run valgrind ./program. Make this routine, not a last resort.

Counting steps: Big-O

Before comparing algorithms you need a way to talk about "how much work" that does not depend on your laptop. Big-O is that language, and it is simpler than its reputation.

Big-O answers one question: as the input gets bigger, how does the amount of work grow? Not "how many seconds", which depends on the machine, but "how does it scale". You count the steps as a function of n, the input size, then keep only the fastest-growing term and drop constants.

See it grow

Drag the slider. Notice how n² and 2ⁿ run away while log n barely moves. This is why binary search (log n) can search a billion items in about 30 steps, and why an O(n²) sort on a million items takes minutes while an O(n log n) sort takes a blink.

How to read code for its Big-O

  1. A loop over n items is O(n).
  2. A loop inside a loop, both over n, is O(n²). Three deep is O(n³).
  3. Something that halves the problem each step (binary search, i *= 2) is O(log n).
  4. A loop that halves inside a loop over n is O(n log n).
  5. Two loops one after the other, not nested: O(n) + O(n) = O(n). Only the biggest term survives.
  6. Calling a function inside a loop costs the function's Big-O times the loop's. strlen inside a loop over a string is O(n²). That is a real bug people ship.

Space complexity works the same way for memory. Merge sort needs an extra array: O(n) space. Quicksort sorts in place: O(log n) for the recursion. You will see both.

What is the time complexity of for (i = 1; i < n; i *= 2) work();?

i goes 1, 2, 4, 8, ... and reaches n after log₂(n) doublings. Any loop that multiplies its counter is logarithmic.

Dynamic arrays

A C array cannot grow. A dynamic array is a C array plus two numbers and a rule for growing. This is exactly what a Python list is underneath.

The structure keeps three things: a pointer to a heap block, how many slots the block has (capacity), and how many are in use (length). Appending is instant while there is room. When the block is full, allocate a new one twice as big, copy everything over, and continue. The doubling is the trick: copying happens so rarely that, averaged over many appends, each one costs O(1). That is called amortized constant time.

Why double the capacity instead of adding 10 slots each time?

Doubling means after n appends you have copied at most about 2n elements total. Adding a constant means about n²/20 copies. Doubling uses MORE memory (up to half the block can be empty) and that trade is worth it.

Searching: linear and binary

Two ways to find a value. One looks at everything. The other throws away half the problem with every question, and only works if the data is sorted.

Linear search

Walk from the start, compare each element, stop when you find it. Nothing to assume about the data. Step through it and watch i move.

Binary search

If the array is sorted, look at the middle. Too small? The answer can only be on the right, so forget the left half. Too big? Forget the right half. Each step halves the search space, so 1,000,000 items need at most 20 looks. Watch the dimmed region grow.

Reading these two side by side

Both have the same contract and the same "return index or -1" convention. The difference is entirely in the loop: linear search's invariant is "the target is not in a[0..i-1]", binary search's is "the target, if present, is in a[lo..hi]". Once you can state an invariant in a sentence, you understand the loop.

The precondition

Binary search on unsorted data returns nonsense without any error. When you read code that calls binary search, your first question is: where was this sorted? If you cannot find the answer, you have found a bug.

Binary search for 23 in {2, 5, 8, 12, 16, 23, 38, 56, 72, 91}. How many times is line 5's comparison executed? (Count the middle elements examined.)

What happens if you write lo = mid instead of lo = mid + 1?

With lo = 4, hi = 5, mid is 4. If a[4] is too small, lo = mid leaves lo at 4. Nothing changed, so the next turn is identical. Forever. The +1 guarantees progress.

Part 2 · DSA in C

Sorting I: the simple sorts

Three O(n²) sorts. You will never ship them, but each teaches a pattern you will use for the rest of your life: swapping, finding a minimum, and shifting to make room.

Bubble sort: swap neighbours

Walk the array, and whenever two neighbours are out of order, swap them. After one full pass the largest element has "bubbled" to the end. Repeat for the rest. Step through it; the teal cells are locked in place.

Selection sort: find the minimum, put it in front

For position 0, scan everything to find the smallest and swap it in. For position 1, scan the rest. Fewer swaps than bubble sort (at most n), same number of comparisons.

Insertion sort: like sorting cards in your hand

Take the next card. Slide the bigger cards one step right until there is a gap where it belongs, and drop it in. On nearly sorted data this is O(n), which is why real libraries use it for small or almost-sorted inputs. The yellow cell is the card in your hand.

What to take from this chapter

  • The swap idiom: three lines and a tmp.
  • The track-the-index idiom: min = j remembers a position, not a value.
  • The shift-right-to-make-room idiom, with the bounds check before the array read. You will use this to insert into any array-based structure.
  • All three are O(n²) because they compare pairs, and there are about n²/2 pairs. To do better, you must avoid comparing most pairs. That is what merge sort and quicksort do.

Which simple sort is fastest on an array that is already sorted?

Insertion sort's inner while loop stops immediately when a[j] is not bigger than key, so each element costs O(1): O(n) total. Selection always scans everything. Bubble sort as written also does all its passes (a "did anything swap" flag fixes that).

An array keeps its elements side by side. A linked list scatters them anywhere in memory and chains them with pointers. Inserting becomes cheap; finding becomes slow.

How to read pointer-rewiring code

Draw it. Every time you see x->next = y, erase the arrow leaving x and draw a new one to y. Deletion code looks hairy in text and obvious on paper. The two rules that prevent almost every list bug: save next before you free, and check for NULL before you follow.

In push_front, what goes wrong if you write head = n; before n->next = head;?

After head = n, the old first node is unreachable. Then n->next = head makes n point at n: a one-node cycle. Every rewiring has an order, and the order is: connect the new thing first, then move the pointers that would lose track of the old thing.

Recursion and the call stack

A function that calls itself. It feels like magic until you see the call stack, and then it is just a stack.

Every recursive function has two parts: a base case that answers directly, and a recursive case that solves a slightly smaller version of the problem and uses that answer. Factorial: 5! = 5 × 4!, and 1! = 1. Step through it and watch frames pile up and then unwind. Each frame is a paused copy of the function with its own n.

How to read recursive code

Do not try to trace every call in your head. Instead:

  1. Find the base case. Confirm it returns without recursing.
  2. Look at the recursive call. Confirm its argument is smaller in some way (n - 1, a shorter list, half the array). If it is not, the recursion never ends.
  3. Trust the recursive call. Assume factorial(n - 1) returns the right answer, and check that the line using it builds the right answer for n. This is called the "recursive leap of faith" and it is the same reasoning as mathematical induction.

Merge sort: split until trivial, then merge back up

Why O(n log n)? Halving n repeatedly reaches 1 after log₂n splits, so the recursion is log n levels deep. At each level, all the merges together touch every element once: O(n). Multiply. Hash tables

Arrays give O(1) lookup by index. A hash table gives O(1) lookup by anything: a word, a name, a key. The trick is turning the key into an index.

A hash function maps a key to a number. Take that number modulo the table size and you have an array index, a bucket. Store the key there. To find it later, hash again and look in the same bucket. Two keys sometimes land in the same bucket (a collision); the simplest fix is to make each bucket a linked list. Type a word and watch where it lands.

apples = 4 no plums

Why it is O(1), and when it is not

If keys spread evenly, each chain holds about n / NBUCKETS entries. Keep the table big enough (grow it when the load factor n / NBUCKETS passes about 0.75) and chains stay short: a constant. If the hash function is bad and everything lands in one bucket, you have a linked list and O(n) lookups. The quality of the hash function is the whole game.

Where you will see this

Python's dict and set, every symbol table in every compiler, caches, database indexes, and the "have I seen this before?" check in dozens of algorithms. In the problem ladder, the move from an O(n²) solution to an O(n) one is very often "use a hash table".

Why does ht_get return int * instead of int?

Returning a sentinel like -1 or 0 collides with legitimate values. A pointer gives a clean "absent" signal. Many C APIs use exactly this pattern.

Heaps and priority queues

A queue where the most important item leaves first, not the oldest. Built on a tree that is cleverly stored in a plain array with no pointers at all.

A tree hiding in an array

Number the nodes of a complete binary tree top to bottom, left to right, starting at 0. Then the children of node i are at 2i + 1 and 2i + 2, and its parent is at (i - 1) / 2. No pointers, no malloc per node, perfect cache behaviour. The heap rule (for a max-heap): every parent is at least as large as its children. The largest element is therefore always at index 0.

Watch values being inserted. Each new value goes at the end and sifts up, swapping with its parent while it is bigger.

Costs and uses

Graphs: BFS and DFS

Nodes and the connections between them. Road maps, social networks, dependency trees, the internet. Two traversals, built on a queue and a stack, cover a surprising share of all graph problems.

Storing a graph

The common choice is an adjacency list: for each node, the list of its neighbours. For a small fixed graph in C, an array of arrays with a degree count does the job; a dynamic version uses a Vec per node.

Breadth-first search: ripples in a pond

Visit the start, then all its neighbours, then all of their unvisited neighbours, and so on in rings. A queue holds the frontier. BFS finds the shortest path in number of edges, which is why it powers "degrees of separation", maze solving, and network routing. Run it and watch the queue.

Depth-first search: follow one path to the end

Go as deep as you can before backing up. The recursion's call stack is the stack. DFS is the tool for "is there any path?", cycle detection, topological sorting, and counting connected components (the "number of islands" problem in the ladder).

Reading graph code

Three questions identify any traversal: What holds the frontier (queue means BFS, stack or recursion means DFS)? When is a node marked visited (on enqueue or on visit)? What happens at the visit (printing, recording distance, checking for the goal)? The same skeleton, with a priority queue as the frontier and edge weights added, becomes Dijkstra's algorithm. You will meet it in the ladder.

Which traversal finds the fewest-edges path from A to B in an unweighted graph?

BFS visits all nodes at distance 1, then all at distance 2, and so on. The first time it reaches B, it did so by a shortest path. DFS may reach B by a long detour first.

Dynamic programming

Recursion that remembers. When a problem breaks into overlapping subproblems, solve each one once, store the answer, and look it up ever after. Exponential becomes polynomial.

Memoization: fix Fibonacci

Naive fib(40) makes 300 million calls because it recomputes the same values. Add an array of remembered answers and it makes 40.

That is top-down DP: the original recursion plus a cache. The other style, bottom-up, fills a table from the smallest case upward with a loop, no recursion at all:

The recipe

  1. Define the subproblem in one sentence. "dp[i] is the fewest coins that make amount i."
  2. Write the recurrence. How does dp[i] follow from smaller entries? "dp[i] = 1 + min over coins c of dp[i − c]."
  3. Set the base case. "dp[0] = 0: zero coins make zero."
  4. Decide the fill order. Smaller amounts before larger ones, so what you need is already there.
  5. Read off the answer. dp[amount].

Coin change, watched cell by cell

Coins {1, 2, 5}, amount 11. Step through and watch each cell get filled from earlier cells. The "∞" means "not reachable yet".

How to recognise a DP problem

  • The question asks for a minimum, maximum, count, or yes/no over many possible choices.
  • A brute-force recursion exists but is exponential.
  • The recursion revisits the same inputs. That is the signal: overlapping subproblems.
  • The best answer for the whole is built from the best answers for the parts (optimal substructure).

Climbing stairs, longest common subsequence, edit distance, knapsack, and longest increasing subsequence are all in the ladder. They look different and are all the same recipe. The hard part is step 1: finding the sentence. Once you have it, the code is ten lines.

Why does min_coins fill dp[1], dp[2], ... in increasing order?

The recurrence reads smaller entries. If dp[i − coin] were still INF because it had not been computed, dp[i] would be wrong. Fill order follows the direction of the dependencies.

Stage 2: a neural network in C

A neural network is matrix multiplications with a nonlinearity between them, trained by following a gradient downhill. Build one with no library and you will understand every framework forever.

The math you must own (do the refresher first)

  • Vectors and matrices. A vector is a 1-D array. A matrix is a 2-D array stored, in C, as one flat 1-D array in row-major order: element (i, j) is at index i * cols + j. That formula is the array indexing from Part 1 and it is the heart of all of this.
  • Dot product and matrix multiply. C = A × B means each C[i][j] is the dot product of row i of A with column j of B. Three nested loops. Cost 2·m·k·n FLOPs.
  • Derivatives and the chain rule. If y depends on u and u depends on x, then dy/dx = dy/du · du/dx. Backpropagation is the chain rule applied layer by layer, from the loss backward.
  • Gradient. The vector of partial derivatives of the loss with respect to every weight. It points uphill; you step the opposite way.
  • Probability basics. Softmax turns scores into probabilities; cross-entropy measures how surprised the model is by the right answer.

The only expensive line: matrix multiply

Everything else is linear in the data. Matmul is cubic, and it is where 90% or more of the time goes in any network. The naive loop order below is correct and slow, and understanding why it is slow is the beginning of performance engineering.

After loop reordering, the next steps are blocking (tiling: work on sub-matrices that fit in cache), SIMD (one instruction on 8 or 16 floats at once, via compiler auto-vectorization or intrinsics), and multithreading (OpenMP). Then you measure against OpenBLAS and discover that a tuned library is still faster, and you read its source to learn why. This exact progression, moved to the GPU, is Stage 3.

Performance concepts you learn here

  • Cache lines and locality. Memory arrives in 64-byte lines. Sequential access is fast; strided access wastes most of each line.
  • Row-major vs column-major and why loop order matters.
  • SIMD (single instruction, multiple data): AVX2 and AVX-512 on x86, NEON on ARM.
  • BLAS (Basic Linear Algebra Subprograms): the standard interface for matmul and friends. sgemm is the function name you will see everywhere.
  • Measuring. time, then perf stat for cache misses and instructions per cycle, then perf record for hot lines.
  • Numerics. FP32 vs FP16 vs BF16, summation order changing results, why you compare with a tolerance.

Stage 3: CUDA and the GPU

A GPU is thousands of simple cores that are only fast when they move together. CUDA is C with a few extra words for telling them what to do. The hard part is not the syntax; it is the memory.

Why a GPU is fast, and when it is not

A CPU core is built to make one thread fast: big caches, branch prediction, out-of-order execution. A GPU gives up all of that for raw count: a modern GPU has over a hundred streaming multiprocessors (SMs), each running thousands of threads, and hides memory latency by switching between them instead of by caching. It wins when the work is the same operation on millions of elements (exactly matmul) and loses when threads disagree about what to do next.

The concepts

TermMeaning
KernelA function marked __global__ that runs on the GPU, once per thread.
Thread, block, gridThreads are grouped into blocks (up to 1024); blocks form the grid. You launch kernel<<<blocks, threadsPerBlock>>>(args). Each thread computes its own index from blockIdx, blockDim, threadIdx.
Warp32 threads that execute the same instruction at the same time (SIMT). If they take different branches, the warp runs both paths serially: divergence.
SMStreaming multiprocessor: the unit that runs blocks. Occupancy is how many warps an SM has resident to switch between.
Global memoryThe GPU's main memory (tens of GB, high bandwidth, high latency). Every byte you read from it should be used as much as possible.
Shared memoryA small, fast, per-block scratchpad you manage by hand (__shared__). The key to tiling.
RegistersPer-thread storage, fastest of all, limited. Using too many lowers occupancy.
CoalescingWhen the 32 threads of a warp read 32 consecutive addresses, the hardware makes one memory transaction. Scattered addresses make 32. The single most important performance rule.
Bank conflictsShared memory is split into banks; threads hitting the same bank serialize. Padding arrays by one element is the classic fix.
TilingLoad a tile of A and B into shared memory once, have every thread in the block reuse it many times. Turns matmul from memory bound toward compute bound.
__syncthreads()Barrier: every thread in the block waits here. Needed between writing shared memory and reading it.
ReductionCombining many values into one (sum, max) in parallel: tree-shaped, with warp shuffles at the end. Softmax and layer norm are reductions.
AtomicsatomicAdd and friends, for when many threads must update one location. Correct but slow if contended.
StreamsQueues of GPU work that can overlap: copy the next batch while computing the current one.
Tensor CoresHardware units for small matrix multiplies in FP16/BF16/INT8. Where the big FLOP numbers come from. Reached via WMMA, cuBLAS, or CUTLASS.
TritonA Python language that compiles to GPU kernels with tiling handled for you. Learn CUDA first so you know what it is doing.

TermMeaning and why it matters
Prefill vs decodePrefill processes the whole prompt at once (big matmuls, compute bound). Decode produces one token at a time (tiny matmuls, memory bound: every step re-reads all weights).
KV cacheStored keys and values for every past token so attention does not recompute them. Size = layers × 2 × tokens × heads × head_dim × bytes. For long contexts it exceeds the weights.
BatchingServing many requests in one forward pass so each weight read is amortized across users. The main lever for throughput.
Continuous batchingAdding and removing requests mid-generation instead of waiting for a whole batch to finish. vLLM and friends do this.
PagedAttentionManaging the KV cache in fixed-size pages like virtual memory, removing fragmentation. The idea that made vLLM. Straight from the operating systems you will study.
FlashAttentionComputing attention in tiles that stay in shared memory, never writing the full score matrix. Fusion plus tiling, exactly Stage 3's lesson.
QuantizationStoring weights in 8, 4, or fewer bits. Fewer bytes to move per token means faster decode. Formats: GGUF (llama.cpp), GPTQ, AWQ, FP8. Each is a tradeoff between accuracy and speed.
Speculative decodingA small model guesses several tokens; the big model verifies them in one pass. More tokens per weight read.
Tensor and pipeline parallelismSplitting one model across GPUs: by slicing matrices (tensor) or by assigning layers (pipeline). Communication becomes the bottleneck.
TTFT, TPOT, tokens/sTime to first token (prefill latency), time per output token (decode latency), and throughput. Every benchmark reports these; learn to report them with hardware, batch size, and sequence lengths stated.
CUDA graphs, kernel launch overheadDecode steps are so small that launching kernels costs more than running them; graphs record and replay a whole step.

The engines, and which to read first

  • llama.cpp / ggml. C and C++, runs on CPUs and every GPU vendor, invented GGUF quantization. The codebase is big but readable with the method from the reading chapter: start at main, follow the calls. Ideal first target because your C transfers directly.
  • vLLM. Python with custom CUDA kernels; the standard open serving engine. Read the scheduler and the paged KV cache manager; those are data structures from Part 2 doing real work.
  • llm.c (Karpathy). GPT-2 training in C and CUDA. Small enough to read completely. Do this one before the other two.
  • tinygrad. A tiny framework whose point is being readable. Shows how a framework lowers tensor ops to kernels.
  • SGLang, TensorRT-LLM, MLC. Read after the above, for specific techniques.

How to make your first contribution

  1. Build it from source and run it. Fix any build problem you hit; those are often your first documentation contribution.
  2. Read for two weeks before writing. Pick one path (loading a model, one decode step) and trace it end to end. Keep notes. Those notes become a blog post.
  3. Reproduce an open issue. Confirm a reported bug on your machine and post exact steps and versions. Maintainers love this and it costs you nothing but care.
  4. Start small and measurable. A doc fix, a failing test, a benchmark script, a small kernel speedup with before/after numbers. Not a rewrite.
  5. Write the pull request like an engineer. What changed, why, how you tested it, the numbers, and what you are unsure about. The next chapter shows exactly how.
  6. Respond to review quickly and without ego. Every comment is free mentoring from someone who knows the code better than you.

What "set apart" looks like at the end of this stage

A GitHub profile with: the C neural network with a speed table, three CUDA kernels benchmarked against cuBLAS, two or three merged pull requests in a real engine, and three or four written posts explaining what you learned with numbers. That profile gets interviews that a certificate never will, because it is evidence rather than a claim.

Writing and arguing like an engineer

The engineers who advance are the ones who can make a case: state a problem, name the tradeoff, recommend, and back it with evidence. This is a learnable skill with a small vocabulary and a few repeatable shapes.

The five rules

  1. Answer first, then explain. "Yes, we should use a hash table, because lookups dominate." Not a story that ends with the answer. In writing this is called BLUF: bottom line up front.
  2. Name the tradeoff explicitly. Every engineering choice gives something up. Saying what you gave up is what separates a decision from a preference.
  3. Use numbers with units and context. "It is faster" is an opinion. "p99 latency dropped from 340 ms to 120 ms on 1,000 requests, same hardware" is a fact someone can check.
  4. State your assumptions and what would change your mind. This makes disagreement productive instead of personal.
  5. Short sentences. One idea each. Define a term the first time you use it. Never hide behind jargon you cannot explain in plain words.

Vocabulary you should use correctly

BottleneckThe one part limiting the whole"The bottleneck is the database, not the API; the API is idle 80% of the time."

Root causeThe underlying reason, not the symptom"The crash was the symptom; the root cause was a use-after-free in the cache eviction."

The tradeoff sentence

Memorize this shape. It answers "why did you choose X?" in one breath:

Template

"I chose X over Y. X gives us A at the cost of B. In this situation A matters more because C. If C changed, I would reconsider Y."

Examples:

  • "I chose a hash table over a sorted array. It gives O(1) lookups at the cost of more memory and no ordering. Lookups are 95% of the operations here and we never need order. If we needed range queries, I would switch to a balanced tree."
  • "I chose INT8 quantization over FP16. It halves memory traffic, so decode is about 1.7× faster, at the cost of a 0.3-point drop on the evaluation set. For this chat product speed matters more than that last fraction of accuracy. For the medical summarizer I would keep FP16."
  • "I chose to fix the bug with a bounds check rather than restructure the loop. It is a two-line change with a small blast radius, at the cost of leaving the confusing loop in place. We ship Friday; I have opened a follow-up issue for the restructure."

Answering common questions: examples to emulate

"Why is this slow?"

Weak: "I think it is probably the database or maybe the loop, I would need to look."

Strong: "I profiled it. 70% of the time is one function, strlen inside the tokenizer loop, which makes it O(n²) on long inputs. Caching the length makes that loop O(n); on a 100 KB input the run went from 4.2 s to 0.3 s. The remaining 30% is file I/O, which I have not touched."

Pattern: measurement, cause, fix, numbers, what is left.

"Should we rewrite it in Rust?"

Weak: "Rust is safer and faster so yes."

Strong: "Not now. The rewrite would cost roughly two months and the current C code's only known problems are two memory bugs, which the address sanitizer found and we fixed last week. A rewrite is justified if we keep finding memory bugs faster than we fix them, or if we need to onboard people who cannot write safe C. I would revisit this in a quarter with the bug counts in hand."

Pattern: a position, the cost, the evidence, the condition that would flip the decision.

"Explain your project in one minute."

Strong: "I wrote a neural network trainer in C with no libraries to understand what PyTorch does underneath. It trains a two-layer network on handwritten digits to 97% accuracy. The interesting part was performance: the naive matrix multiply took 40 seconds per epoch; reordering the loops for cache locality took it to 6, and OpenMP across 8 cores to 1.1. The main lesson was that memory access patterns mattered more than the arithmetic. Next I am porting the matmul to CUDA."

Pattern: what, why, result, the hard part with numbers, lesson, next step.

"What would you do differently?"

Strong: "I would write the benchmark first. I optimized for two days before measuring and spent most of it on a function that was 4% of runtime. Measuring first would have pointed me at the matmul immediately."

Pattern: a specific mistake, the cost, the concrete change. Never "nothing".

"I don't know."

Strong: "I don't know the exact answer. My guess is that it is memory bound, because decode re-reads all weights per token, but I have not profiled it. If you need a firm answer I can have profiler numbers by tomorrow."

Pattern: admit it, give your best reasoning with its basis, say how and when you would find out. This answer builds more trust than a confident guess.

Disagreeing with someone senior

Strong: "I see it differently, and I may be missing context. My concern is that the new cache has no eviction, so memory grows without bound; on the 10k-request test it reached 9 GB. What would you want to see to be convinced that is a problem, or is there a bound I am not seeing?"

Pattern: name the disagreement, give the evidence, invite the counter-evidence. Attack the problem, not the person.

Giving an estimate

Strong: "Three days if the file format is as documented; a week if it is not, because I would have to reverse-engineer it. I will know which by tomorrow noon."

Pattern: a range tied to a named uncertainty, and a date by which the uncertainty resolves.

How to practise

  • Every project README gets the structure: what, why, how to run, results with numbers, what you learned, what is next.
